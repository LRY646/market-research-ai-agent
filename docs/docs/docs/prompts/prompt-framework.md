# Prompt Engineering 框架说明

本文档说明各类节点的 Prompt 设计思路，不逐字复制完整 Prompt，而是解释每类设计决策背后的逻辑。

---

## 1. 整体 Prompt 设计原则

### 原则一：每个节点只回答一个清晰的研究问题

每个研究模块的 Prompt 都从一个明确的 Research Question 出发：

```
Usage Scenario Agent：
"这个产品在什么情境下被使用？消费者想完成什么任务？"

Target Consumer Agent：
"20-35岁城市上班族有什么生活和饮食特征？"
```

这样做的目的是避免模型在一个 Prompt 中同时承担搜索、推断、综合和结论的任务，减少"自我证明"的倾向。

### 原则二：主动要求标注不确定性

每个研究模块的 Prompt 都要求模型在得出结论时区分：

- 这是搜索到的事实，还是基于搜索结果的推断？
- 这个数据的口径是什么？
- 这个来源的层级是什么？

明确要求标注，比依赖模型"自觉"诚实效果更稳定。

### 原则三：明确写出禁止事项

Prompt 中不仅写"要做什么"，还明确写"不能做什么"。

例如：

```
不能用"复合调味品市场规模"直接代表"黑椒汁市场规模"。
不能因为某个品牌在强调某卖点，就推断消费者一定有这个需求。
不能把"搜索结果经常出现"等同于"市场热度高"。
```

这类禁止性指令在实际运行中对减少口径混用和推断事实化有明显效果。

## 2. 研究模块 Prompt 框架

每个研究模块的 Prompt 通常包含以下结构：

```
Role（角色定义）
↓
Research Objective（本模块要回答的核心问题）
↓
Search Requirements（搜索方向与关键词建议）
↓
Source Quality Rules（来源分级要求）
↓
Evidence Classification Requirements（结论的证据标注要求）
↓
Structured Output Format（JSON 输出格式规范）
```

### Role 设计

Role 不是简单的"你是一个市场研究分析师"，而是针对模块功能做定制：

- 品类市场模块：强调"区分不同统计口径，不做口径混用"
- 目标消费者模块：强调"研究人的生活方式，不是研究产品"
- 社媒趋势模块：强调"区分 Brand Content、Creator Content 和 UGC"

### Search Requirements 设计

Search Requirements 不只是给关键词，还指定搜索优先级：

1. 优先搜索官方来源（品牌官网、行业协会、政府数据）
2. 其次搜索专业研究机构报告
3. 再次搜索主流商业媒体报道
4. 最后参考社媒、电商等定性内容

并要求模型在搜索过程中记录实际访问的页面，而不是引用的来源。

## 3. Source Quality Rules 的 Prompt 设计

这是减少来源误判的核心 Prompt 设计。

关键设计点：

```
判断规则：
- Source Tier 按「你实际访问的页面」来判断
- 不是按文章里面引用了谁来判断

示例：
- 你访问的是网易文章，文章里引用了 Euromonitor → Tier 3（不是 Tier 2）
- 你访问的是 Euromonitor 官网报告摘要 → Tier 2
- 你访问的是京东商品页面 → Tier 4（可辅助观察产品信息，不作为品牌官方资料）
```

实际运行发现：如果不明确写出这个区分，模型极容易把"引用了权威来源的文章"当作权威来源本身。

---

## 4. Evidence Status 标注的 Prompt 设计

每个模块的 Prompt 都要求对每一条核心结论标注 Evidence Status：

```
在你输出的每一条核心结论后面，用以下格式标注：
（证据状态：已验证事实 / 行业趋势 / 分析推断 / 待验证假设）

区分方式：
- 有直接来源支持的，写"已验证事实"或"行业趋势"
- 你基于多个信息点推断出来的，写"分析推断"
- 你认为值得验证但暂无直接证据的，写"待验证假设"
- 不要把分析推断写成已验证事实
```
